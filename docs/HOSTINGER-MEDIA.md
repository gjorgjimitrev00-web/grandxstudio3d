# Persistent Hostinger media

## Chosen architecture

Use **two independent websites in the same Hostinger Cloud Startup account**:

1. The Next.js store, deployed from GitHub.
2. A PHP/HTML website assigned to `media.your-domain.mk` (or a temporary Hostinger hostname while waiting for a domain).

The store never writes runtime files into its repository, `.next`, `public`, Node application directory, or `/tmp` in production. A signed HTTPS request transfers optimized image bytes or a private attachment to a small PHP bridge. The media site's files are managed separately with Hostinger File Manager and are **not** connected to the store's GitHub deployment.

Hostinger documents creating an independent subdomain website on the same hosting account. This is the basis for separation, not a claimed guarantee about the Node deployment filesystem. Confirm the extra PHP website fits your existing plan's website quota and run the actual redeploy test before launch. No external paid storage is involved.

## Exact layout

In the independent media website's File Manager root, create:

```text
media-website-root/
  grandx-media-config.php           # private configuration; outside public_html
  grandx-private/                  # private originals; permission 0700
  public_html/
    .htaccess                     # from deployment/media/public_html/
    bridge.php                    # from deployment/media/public_html/
    images/                       # public optimized images; permission 0755
      <random-uuid>-400.webp
      <random-uuid>-800.webp
      <random-uuid>-1600.webp
```

Do not assume a universal `/home/u123/...` path. Use the **actual independent media website root** visible in your File Manager. `bridge.php` resolves its config as `dirname(__DIR__) . '/grandx-media-config.php'`, and the sample config places private files beside that config. This avoids guessing user IDs or deployment paths.

1. Add a **Custom PHP/HTML website**, entering the media subdomain during onboarding. Use the independent website method, not a subfolder of the Node app. Enable SSL and PHP 8.2+.
2. Copy `deployment/media/public_html/bridge.php` and `.htaccess` into that website's `public_html` using File Manager.
3. Copy `deployment/media/config.example.php` to **one directory above public_html**, naming it `grandx-media-config.php`.
4. Replace its `secret` with the same independent 64-character random secret used for `MEDIA_UPLOAD_SECRET` in the Node app. Set config permission to 0600 if supported by the account's PHP file owner. Never put the config or private directory under public_html. Never commit the configured copy.
5. Create `grandx-private` beside the config (0700) and `public_html/images` (0755), owned by your hosting account. The bridge can also create them on first use. Files are private 0600 or public 0644. Do not use 0777.
6. Set PHP `post_max_size` to at least 24M, `upload_max_filesize` to at least 20M, and a sufficient memory limit such as 128M in hPanel. Incoming Node multipart requests are limited separately to 20 MB per private attachment and 10 MB per image (up to three images per request). Set proxy request limits accordingly if configurable.
7. In the Node app environment set:

```dotenv
MEDIA_DRIVER=bridge
MEDIA_BASE_URL=https://media.your-domain.mk
MEDIA_UPLOAD_URL=https://media.your-domain.mk/bridge.php
MEDIA_UPLOAD_SECRET=<same-secret-as-private-PHP-config>
```

The configured URLs must use HTTPS. Node rejects redirects when calling the bridge, preventing secret-bearing requests from following redirects to another origin. There is no browser CORS access to the upload endpoint.

## Protocol and public URLs

The Node app sends POST requests with `X-GX-Action` (`put`, `get`, `delete`), `X-GX-Key`, `X-GX-Time` (Unix seconds), and `X-GX-Signature`. Signature = HMAC-SHA256 of `action + newline + key + newline + timestamp + newline + SHA256(body)` using the secret. Requests older than five minutes, invalid signatures, invalid storage keys and oversized bodies are refused.

Uploads use UUID filenames generated by Node and exclusive creation on the PHP side, preventing overwrite/collision. An uploaded JPEG is decoded, auto-oriented, stripped of metadata, converted to WebP and resized with no upscaling. The bridge independently confirms that public content is WebP no larger than 1600×1600.

Public product URLs are `https://media.your-domain.mk/images/<uuid>-800.webp` (listing), `-400.webp` (thumbnail) and `-1600.webp` (detail). Prisma stores all three URLs, the filename UUID, image dimensions, alt text, sort order, primary flag and product relationship.

Private files have internal keys `private/<uuid>.stl`, etc. They have **no public URL**. An admin clicks `/api/admin/files/<database-file-id>`; the Next server authorizes the admin, fetches bytes through a signed bridge request, and returns an attachment. Anonymous requests cannot download them even if they know a file ID or key. Files are never parsed as PHP, served inline, unzipped or executed. MIME declarations on model files are not trusted as proof of safety.

## Delete and replacement behavior

Deleting an image removes its database reference, then deletes all three sizes when no other product image record references the filename. If physical deletion fails after the database change, it leaves an orphan, not a broken order. Run the media inventory check and remove unreferenced UUID families during maintenance after backup. Product deletion preserves historical order snapshots and may retain media for those snapshots; it does not automatically erase all historical image bytes. Category image replacement may leave an unreferenced old image family. Private files are retained with their request until you apply your reviewed retention policy and delete both records and stored files through an authorized maintenance procedure.

Duplicated products share media references; editing a duplicate’s text, variants or gallery ordering is independent. Do not delete shared media manually while any product uses it.

## Mandatory deployment survival test

This test **cannot be claimed complete without access to your actual Hostinger account**.

1. Deploy the Node store and independent media website.
2. Sign in as admin. Create a test product, upload JPEG/PNG images and publish it.
3. Record image URLs, byte sizes and SHA-256 hashes. Verify each public URL loads on desktop and mobile.
4. Submit a custom print request with a non-sensitive sample STL; confirm anonymous direct requests fail and an authenticated admin can download identical bytes.
5. Push a harmless text change to GitHub and let Hostinger redeploy **only the Node store**.
6. Restart the Node app as a separate check.
7. Re-open every recorded image URL and compare the hashes. Open the product and re-download the private STL as admin. Verify the order/database records also remain.
8. Confirm the media site's directories, config and data were not replaced. Only after this passes should you accept real customer uploads.

If anything disappears, stop launch, inspect which website/paths Hostinger deployed, and correct the separation. Do not fall back to saving into `public/uploads` or the Node deployment directory.

## Backup and restore

- Use Hostinger's backup controls or File Manager download for `public_html/images`, `grandx-private` and the private config. Keep an encrypted copy outside the hosting account according to your retention policy.
- Export MySQL through hPanel/phpMyAdmin at the same time so URLs, file IDs, products and private file metadata match the stored bytes.
- Source code and bridge code are backed up in GitHub; uploaded images, private designs, configuration secrets and database contents are not.
- Restore to a separate staging media website and staging database first. Verify one image family and one authenticated private-file download before restoring production.
- Rotate the shared media secret by updating both private PHP config and hPanel Node env together, then redeploy/restart the Node app. Never put the media secret in browser code.
